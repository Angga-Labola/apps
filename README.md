# Application feature guide

This repository contains a FastAPI application with a local-file Bible reader
and a LetsLogic-powered Sokoban game. The feature routers are registered in
`app.py`; browser assets are served from `static/`, and HTML pages and Bible
chapter files live under `templates/`.

Run the app locally with:

```powershell
uvicorn app:app --reload
```

## Bible reader

### Source files and data

- `bible_router.py` implements the Bible page, chapter catalog, local chapter,
  and commentary routes.
- `templates/bible_reader.html` is the shared chapter-reader interface.
- `static/bible-reader.js` reads the passage from the URL, builds the controls,
  fetches chapter HTML, and handles navigation.
- `templates/commentary_reader.html` and `static/commentary-reader.js` provide
  the separate commentary page and its navigation/rendering.
- `templates/bible/<BOOK>/<BOOK>_<CHAPTER>.html` holds the local chapter
  source. For example, `templates/bible/GEN/GEN_2.html` is Genesis 2.
- `bible_list.py` and `bible_copier.py` are standalone API helper scripts, not
  part of the web request flow. `bible_copier.py` currently has its Bible ID,
  book ID, chapter count, and output directory specified in the script. Its
  output goes to a `bible/` directory, which must be reviewed and copied into
  the reader's `templates/bible/<BOOK>/` tree to become available to the app.

The reader's catalog is generated by scanning the local chapter files for the
book IDs listed in `bible_router.py`. The chapter HTML is not fetched from the
Bible API at page-view time. The standalone downloader uses `BIBLE_API_URL`
and `BIBLE_API_KEY` from its environment or `.env` file.

### Routes

| Route | Purpose |
| --- | --- |
| `/bible` | Opens the reader's default/first available chapter. |
| `/{book_id}/{chapter_id}` | Validates a local chapter and serves the shared reader page, e.g. `/GEN/2`. |
| `/api/bible/books` | Returns the books and chapter numbers found in local files. |
| `/api/bible/{book_id}/{chapter_id}` | Returns the validated chapter HTML for the reader to display. |
| `/commentary/{commentary_id}/{book_id}/{chapter_id}` | Serves the commentary page for a selected author and passage. |
| `/api/bible/commentary/{commentary_id}/{book_id}/{chapter_id}` | Fetches the selected chapter commentary from `https://bible.helloao.org`. |

Page URLs and API URLs have different roles. For example, `/GEN/2` is the
reader page while `/api/bible/GEN/2` returns only that chapter's HTML. This
gives each chapter a stable URL and lets Giscus associate discussions with
chapter paths.

### Page and navigation flow

1. FastAPI checks the requested book, numeric chapter, and corresponding local
   HTML file, then returns the shared reader template.
2. `static/bible-reader.js` requests `/api/bible/books` and populates the book
   selector. It reads the requested passage from the URL; an optional
   `?verse=<number>` selects and scrolls to a verse.
3. If the path is absent or points to a chapter that is not available, the
   script navigates to the first available chapter.
4. The script fetches the chapter API route, parses its HTML, filters out the
   source image, line breaks, and source heading, and inserts the remaining
   chapter content into the page.
5. Selecting a book or chapter and using Previous/Next navigates to a new
   chapter URL. Navigation crosses to the previous or next book at book
   boundaries. Browser Back and Forward work through those same URLs.
6. A request counter prevents a slow response for an earlier chapter from
   overwriting the currently selected chapter.

Unknown books and missing chapter files return HTTP 404. If the catalog or
chapter request fails, the page displays the error and disables controls that
depend on the missing data.

### Commentaries and discussions

The reader supports John Calvin (`john-calvin`), John Gill (`john-gill`),
Matthew Henry (`matthew-henry`), and Jamieson-Fausset-Brown
(`jamieson-fausset-brown`). Selecting one and clicking **Open** launches a
separate commentary page for the current passage. That page gets commentary
through the backend API, displays available source and license links, and
provides Previous/Next chapter navigation. Availability varies by author and
chapter; an unavailable commentary is shown as an error/availability message.

The backend only accepts the configured commentary IDs. It validates that the
requested passage exists locally, calls the upstream API with a timeout, and
returns the structured commentary data and attribution. The browser renders
commentary using text nodes rather than inserting upstream HTML.

Giscus is embedded in the Bible reader template with pathname mapping. Each
chapter URL therefore maps to its own GitHub Discussion; verses in the same
chapter share that discussion. Chapter changes are full page navigations so
Giscus can initialize for the new path. If Giscus cannot find a discussion, it
may create one when a visitor comments or reacts.

## Sokoban

### Source files and gameplay

- `sokoban_router.py` serves game pages, contacts LetsLogic, persists
  collections, and exposes the game APIs.
- `sokoban_solver.py` parses supported maps and performs bounded search for
  solvability or a concrete move sequence.
- `templates/sokoban.html` and `static/sokoban.js` provide the game board,
  collection browser, movement, undo/restart, and solution playback.
- `templates/sokoban_import.html` and `static/sokoban-import.js` provide the
  LetsLogic collection import page.
- `static/sokoban.css` contains game-specific styling; common site styles are
  in `static/styles.css`.
- `tests/test_sokoban_solver.py` and `tests/test_sokoban_api.py` cover the
  solver and API behavior.

Open `http://127.0.0.1:8000/sokoban` to play or
`http://127.0.0.1:8000/sokoban/import_collections` to browse LetsLogic
collections. A built-in practice level is available even when LetsLogic is
unconfigured or unreachable.

The import page requests collection metadata from this app's backend. Choose a
collection and click **Import** to have the backend fetch and persist it.
Return to the game, choose it under **Saved collections**, and open it to list
its levels. The game supports keyboard arrows/WASD, on-screen movement
controls, undo, restart, and level navigation. Fullscreen expands the board
view, which scrolls to keep the player visible.

### Configuration and storage

Set `SOKOBAN_KEY` in `.env` for local development or as a Vercel environment
variable. The key is used only by the backend and is never sent to browser
JavaScript. `SOKOBAN_COLLECTION_ID` sets the default collection for the legacy
`/api/sokoban/levels` endpoint (default `550`).
`SOKOBAN_COLLECTIONS_DIR` overrides the local JSON collection directory,
which defaults to `data/sokoban/collections/`.

On Vercel, connect a Vercel Blob store to the project. Its credentials are
used by the Vercel Blob SDK; `BLOB_READ_WRITE_TOKEN` may also be configured
when needed. `SOKOBAN_BLOB_ACCESS` must match the store's access mode
(`public` or `private`, default `public`). Local mode saves each collection as
a JSON file; Vercel mode saves it under `sokoban-collections/<id>.json`.
Game progress and solver caches are held only in browser memory and are lost
when the page is reloaded.

The saved-collection delete button asks for confirmation, but deletion has no
additional authentication: any visitor who can access the public site can
delete a saved collection. Configure deployment access accordingly if that is
not acceptable.

### Sokoban routes

| Route | Purpose |
| --- | --- |
| `/sokoban` | Serves the game page. |
| `/sokoban/import_collections` | Serves the LetsLogic import page. |
| `/api/sokoban/health` | Reports whether `SOKOBAN_KEY` is configured, without returning it. |
| `/api/sokoban/collections` | Lists available LetsLogic collections. |
| `/api/sokoban/collections/{collection_id}/download` | Fetches and saves a LetsLogic collection. |
| `/api/sokoban/saved-collections` | Lists locally or Blob-persisted collections. |
| `/api/sokoban/saved-collections/{collection_id}` | Reads a saved collection. |
| `/api/sokoban/saved-collections/{collection_id}/levels/{level_index}/solve` | Checks one saved level; `show_solution=true` requests a move sequence. |
| `/api/sokoban/saved-collections/{collection_id}` (DELETE) | Deletes a saved collection. |
| `/api/sokoban/levels` | Legacy endpoint for the configured default collection. |
| `/api/sokoban/levels/download` | Downloads the configured default collection as JSON. |

### Solver behavior and limits

Maps may be supplied as text rows, arrays of rows, or the supported compact
numeric tile encoding with width and height. In text maps, `#` is a wall,
`@` is the player, `$` is a box, `.` is a goal, `*` is a box on a goal, and
`+` is a player on a goal. Exactly one player and at least one box and goal
are required.

The local solver searches box pushes rather than every player step. It groups
player positions that are reachable without pushing into one equivalent
search state, prunes boxes that cannot reach any goal and certain non-goal
2-by-2 deadlocks, and uses breadth-first search over those push states. Search
is capped at 25,000 states or 3 seconds. Hitting a cap returns `unknown`, not
`unsolvable`.

The **Check** action may use positive `blue_moves` or `green_moves` metadata
from LetsLogic as evidence that the level is solvable. **Show solution** must
find a concrete local move sequence, so a level can be known-solvable while
sequence search returns `unknown`. A returned sequence uses lowercase
`u/d/l/r` for player walking and uppercase `U/D/L/R` for box pushes. Playback
steps forward or backward one move at a time.

The browser caches a found move string and solvability result by level index
for the currently loaded collection. The solution cache is in-memory only; it
is reset when another collection is loaded or the page is reloaded. An
`unknown` sequence-search result is not cached as a solution.

## Running tests

Run the focused Sokoban tests with:

```powershell
python -m unittest discover -s tests -p "test_sokoban*.py"
```
